# Google Play subscriptions

Payments supports the 4-week SkyCofl Premium (`l_premium`) and Premium+ (`l_prem_plus`) plans for `com.coflnet.sky`. Google Play bills the customer and remits tax. The Play flow uses Google’s checkout and has no Coflnet discount codes, creator codes, or early-performance declaration. Customers manage cancellations and renewals in Google Play. Tier changes in the app are out of scope for this phase.

## Owner setup

1. Apply [the CockroachDB migration](../Migrations/20261121134048_GooglePlaySubscriptions.cockroach.sql) by hand after TermSwitch, before deploying Payments. It adds the nullable `"Subscriptions"."ProviderToken"` text column and records the migration in EF history.
2. In Play Console, create two subscription products for `com.coflnet.sky`, each with one active auto-renewing base plan billed **every 4 weeks**. Use the same base plan ID for both, for example `p4w`. Set regional prices and availability. Configure grace period and account hold. Leave offers disabled for phase 1. [Play Console subscription setup](https://support.google.com/googleplay/android-developer/answer/140504)
3. Enable the Google Play Android Developer API. Grant the Payments service account access to this app and the Play Console permissions to view financial data and manage orders and subscriptions. Give Payments the credentials through the existing `GOOGLEPAY:ServiceAccountKeyFile` setting. Set `GOOGLEPAY:PackageName` to `com.coflnet.sky`. [Google Play Developer API setup](https://developers.google.com/android-publisher/getting_started)
4. Configure the actual Play product IDs and push settings before enabling sales.

| Key under `GOOGLEPAY` | Value |
| --- | --- |
| `SUBSCRIPTION_PLANS` | Play product ID → Payments plan slug, for example `{"premium":"l_premium","premium_plus":"l_prem_plus"}`. A configuration section works too, for example `GOOGLEPAY__SUBSCRIPTION_PLANS__premium=l_premium`. An empty mapping disables eligibility. |
| `BASE_PLAN` | Exact Play base plan ID. Defaults to `p4w`. |
| `ALLOWED_REGIONS` | Optional comma-separated ISO alpha-2 regions, for example `DE,AT`. Empty allows all. With a list set, a missing or disallowed Google billing region prevents the first grant and acknowledgment. Existing granted subscribers are unaffected. Keep it aligned with Play Console availability. |
| `PUBSUB_AUDIENCE` | Exact audience configured on the authenticated push subscription. Use the production webhook URL if using the Pub/Sub default audience. |
| `PUBSUB_SERVICE_ACCOUNT` | Email of the push authentication service account. Payments checks the Google-signed token’s issuer, audience, account email, and `email_verified` claim. |
| `ACCEPT_TEST_PURCHASES` | Defaults to `true`. Play license-test purchases can grant access and never create a real subscription payment record. Set to `false` when you want to reject them. |

The Android Publisher service account and the Pub/Sub push identity serve different purposes. Store the Android Publisher credentials in the existing secret configuration.

## Pub/Sub and RTDN

1. Create a Cloud Pub/Sub topic. Grant `roles/pubsub.publisher` on the topic to `google-play-developer-notifications@system.gserviceaccount.com`.
2. In Play Console, open the app’s monetization setup and set the full topic name (`projects/PROJECT_ID/topics/TOPIC_ID`). Select notifications for subscriptions and one-time products to retain CoflCoins purchase and void handling. [Play RTDN setup](https://developer.android.com/google/play/billing/getting-ready#configure-rtdn)
3. Create an HTTPS push subscription on the topic pointing to `/callback/googlepay` on the Payments host. Enable authentication and select a dedicated user-managed service account. Give the Pub/Sub service agent permission to mint its OIDC tokens (`roles/iam.serviceAccountTokenCreator` on that account), and the operator creating the subscription permission to act as the account. Match the configured push identity and audience to the two Payments settings. [Authenticated Pub/Sub push](https://docs.cloud.google.com/pubsub/docs/authenticate-push-subscriptions)
4. Set the push subscription retry policy to exponential backoff with a minimum of 60 seconds and a maximum of 600 seconds. Pub/Sub push backoff applies across the subscription, so repeated failures can slow all Play notifications. [Retry policy](https://docs.cloud.google.com/pubsub/docs/subscription-retry-policy) and [push backoff](https://docs.cloud.google.com/pubsub/docs/push#push_backoff).
5. Send a test notification from Play Console. Both standard Pub/Sub JSON envelopes and payload unwrapping are supported. Invalid OIDC returns 401. A processing failure returns 500 so Pub/Sub can retry. Deliberately ignored notifications return 200.

Both `PUBSUB_AUDIENCE` and `PUBSUB_SERVICE_ACCOUNT` are required. Missing either setting or failing any OIDC check returns 401. This applies to all notifications at `/callback/googlepay`, including CoflCoins. The app's `/api/googlepay/verify` top-up flow is unaffected by these push authentication settings.

## Backend flow

- `GET /api/googleplay/subscription/eligibility?userId=…&productSlug=l_premium` returns `eligible`, `reason`, `playProductId`, `basePlanId`, and `blockingProvider`. Check this before opening Play Billing. A renewing subscription in the same product line blocks checkout, including another Play subscription. A cancelled subscription with a recorded end date no longer blocks checkout.
- At purchase launch, the app should set Play Billing’s `obfuscatedAccountId` to the same non-PII Payments user identifier used for eligibility. For a verified linked token the backend can inherit the previous subscription’s user. A new token without that ID can bind to the user supplied to app completion. An RTDN sync without a resolved user yields `missing_user` internally and leaves the purchase unacknowledged for app restore.
- For a resubscribe through the Play Store after expiry, RTDN can bind the new purchase using the expired account identifier or a known expired purchase token in `outOfAppPurchaseContext`. After granting the new purchase, Payments acknowledges it and leaves the expired subscription and its granted periods unchanged. [Google Play API reference](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.subscriptionsv2#OutOfAppPurchaseContext)
- `POST /api/googleplay/subscription/complete` accepts `userId`, `packageName`, `subscriptionId`, and `purchaseToken`. Google’s response determines the plan and supplies the account binding when available. The response has `isValid`, `status`, and `errorMessage`. A pending payment returns `isValid: false` with status `pending`. Repeating completion for an already granted, valid purchase succeeds without granting twice. Concurrent completion while the token is busy returns HTTP 409 with status `processing`. Publisher HTTP 400 or 404 returns HTTP 500 with error `verification_unavailable`. Retry afterward. Purchases with an `offerId` are unsupported in phase 1.
- RTDN fetches the current state from `purchases.subscriptionsv2.get`. Orders are granted once per latest successful order ID. Grace extends access through the expiry Play reports. Hold and pause suspend access. For a revoke notification, Payments requires `SUBSCRIPTION_STATE_EXPIRED` with `canceledStateContext` and a matching voided order before reversing the paid grant. The cancellation context can also describe an ordinary expiration. An unconfirmed revoke follows normal state synchronization.
- An explicit quantity-based partial refund (`refundType=2`) logs a warning and returns 200. Other refund types, including an omitted `refundType`, require confirmation by `purchases.voidedpurchases.list` with `type=1`, searching the last 30 days and matching both order ID and purchase token. A voided-list failure always returns 500, and Pub/Sub message expiry bounds retries. If the list succeeds without a match, the webhook returns 500 for event times within the past 24 hours or up to 5 minutes in the future. Older, undated, or further-future misses log a warning and return 200. Missing order ID or purchase token also logs a warning and returns 200. A confirmed refund for a prior order reverses its grant and preserves the newer period. A confirmed latest-order refund marks the local subscription expired until the next renewal sync (S4).
- Renewing Play subscriptions block new Stripe, PayPal, and Lemon Squeezy subscriptions in the same product line with `active_play_subscription`. A pending Play purchase without a grant does not block web checkout. An already paid checkout that overlaps a renewing subscription still grants its paid period and increments `payments_google_play_double_subscriptions_total`.
- A six-hour sweep reconciles non-expired Play subscriptions and retries acknowledgments. Purchases are acknowledged after the grant succeeds. Of the Publisher error responses, only HTTP 410 expires the local subscription row. HTTP 400 or 404 returns 500 from the webhook for retry and leaves the row unchanged during reconciliation, even when `EndsAt` has passed. Checkout eligibility excludes rows with an end date, and expired rows leave the sweep. Existing granted access runs through its recorded expiry. The account subscription response exposes `manageUrl` and leaves resume and tier-change capabilities off.

A sweep can only see the latest successful order in Play’s subscription snapshot. To audit multiple missed billing periods or reconcile historical amounts, use Play order reports. Local payment records use the recurring price and the first purchase time or the local grant time for renewals. A first purchase rejected for its region receives no grant or acknowledgment and creates no manual refund. Google automatically refunds unacknowledged purchases after three days. Existing granted subscribers continue through normal renewal synchronization.

## Test plan

- With a license tester, buy each plan, retry completion, and replay the RTDN. Verify one paid period per order and no real payment record.
- Let a test subscription renew. Verify the new order extends access once. Exercise grace, hold, recovery, cancellation and expiration. Confirm the cancelled period remains accessible until expiry and checkout becomes eligible.
- Refund and revoke the current order in Play Console. Confirm the paid grant is reversed once Google returns the expired state, cancellation context, and matching voided order. Check that an unconfirmed revoke synchronizes normally. Verify that voided-list failures return 500 regardless of event time. For a successful list with no match, verify 500 within the past 24 hours and up to 5 minutes ahead, and a warning and 200 for older, undated, or further-future events. Missing order IDs or purchase tokens and explicit quantity-based partial refunds must warn and return 200 without a list call. Verify a void with an omitted `refundType` still checks the list. Use Publisher fixtures for a matching latest-order void while the subscription is still active and verify local expiration until the next renewal sync (S4). A verified void for a prior order should preserve the newer period. [Voided Purchases API](https://developers.google.com/android-publisher/voided-purchases)
- Check both cross-provider blocks and that an ungranted pending Play purchase permits web checkout. Complete an already paid overlapping checkout and check the warning and counter. Verify that a disallowed or missing first-purchase region prevents grant and acknowledgment without creating a manual refund, and that existing granted subscribers remain unaffected.
- Exercise authenticated push delivery, missing either OIDC setting, invalid issuer/audience/account/verification, and retry after a transient failure. Verify that app top-up verification still works and that a lost response after a one-time purchase was credited and acknowledged can be retried successfully.
- Complete a new token without an obfuscated account ID using the app user. Verify that an RTDN sync without a resolved user yields `missing_user` without acknowledgment. Check offer rejection and HTTP 409 `processing` during concurrent completion.
- Simulate HTTP 410 and verify the local row expires. For HTTP 400 and 404, verify that the renewal webhook returns 500 and preserves the row and paid access, including for a past `EndsAt`. Replay the renewal after Google recovers and verify it grants the new order once.
